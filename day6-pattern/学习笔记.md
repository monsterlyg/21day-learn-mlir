# Day 6：自定义 Dialect、ODS 与 TableGen

## 本日目标

学会把领域语义建模为自定义 MLIR 方言，理解 Operation 定义的组成，以及 ODS/TableGen 如何生成重复的 C++ 样板代码。

## 知识点

### 1. 为什么定义自定义 Dialect

自定义 Dialect 适合表达项目特有的抽象，例如融合算子、NPU 指令、模型层或量化语义。好的高层 Op 应保留优化所需的信息，同时避免过早暴露实现细节。自定义 IR 需要明确语义，不能只是给任意计算换个名字。

### 2. ODS / TableGen

- ODS（Operation Definition Specification）是描述 Dialect、Operation、Type、Attribute、约束和接口的声明式 DSL。
- TableGen 根据定义生成 Op 类、访问器、构建器、parse/print/verify 等代码片段。
- `.td` 是定义来源；生成的 `.inc` 是构建产物，应理解生成关系而非手工维护产物。
- CMake/TableGen 目标、include path 和生成文件接入共同构成构建链。

### 3. Operation 定义的主要部分

- 名称和 Dialect；
- operands（运行时 SSA 输入）；
- results（输出及其类型约束）；
- attributes（静态配置/元数据）；
- regions/successors（嵌套计算和控制流，如需要）；
- traits、interfaces、assembly format、文档说明；
- verifier 或类型推导约束。

ODS 的声明主要规定结构，不会自动定义算子的完整数学含义或 lowering。

### 4. Assembly Format、解析和打印

Assembly format 决定自定义文本 IR 如何打印和解析。显式格式可提升可读性，也可能要求用户提供更多类型/属性。Generic operation form 能以统一结构表达操作，便于调试定义或处理未知操作。Parse 成功仍需经过 verifier。

### 5. Type 与 Attribute 的自定义

自定义 Type 用于表达领域类型语义；自定义 Attribute 用于不可变静态参数。参数类型、storage、mnemonic、parse/print 都要一致。若数据本质上是运行时 SSA 输入，就不应为了方便塞进 Attribute。

### 6. 约束、Traits、验证与语义

- ODS 约束可限定 operand/result/attribute 的类型和值域。
- Trait 表达通用结构性质或已知行为标记。
- Verifier 可验证操作内部一致性和跨字段关系，例如 rank、shape、参数数量之间的约束。
- Type inference 可根据输入和属性推导结果类型；它和 verifier 相关但不等同。
- 副作用、可折叠性、可推导类型等行为必须如实描述，否则通用优化可能做出错误假设。

### 7. 注册和插件

Dialect 在 Context/Registry 中注册后，解析器和工具才能按定义识别其操作、类型和属性。静态链接与动态插件是不同部署方式；插件 ABI/版本需与所用 MLIR 构建相匹配。若 Pass 创建该 Dialect 的操作，也要确保它已注册。

### 8. Dialect 设计原则

- 每个 Op 语义要精确且可验证。
- 高层与低层操作应有清晰的抽象边界。
- 属性命名、类型约束、shape 规则、副作用声明应一致。
- 尽量复用标准方言和接口，只有确实需要项目语义时才新增方言。
- 设计时同时考虑打印、测试、转换和后续维护。

## 练习建议

设计一个带输入、属性和结果的简单 Op：写清数学语义、允许的类型/shape、错误条件、文本形式，以及它将来如何 canonicalize 或 lower。再用合法/非法 IR 检查 verifier。
