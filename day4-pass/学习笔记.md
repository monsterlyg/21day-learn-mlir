# Day 4：Pass 基础设施与 IR 分析

## 本日目标

理解 Pass 是如何组织编译流水线的处理阶段，掌握 Pass 作用范围、遍历、注册和只读分析的基本方法，并区分简单手工检查与正式 Analysis Framework。

## 知识点

### 1. 什么是 Pass

Pass 是针对某类 Operation 执行的一步处理，可以分析、验证或变换 IR。Pass 通过 pipeline 组合成编译流程；一个 Pass 通常不承担整个编译任务。

```text
输入 IR → Pass A → Pass B → Pass C → 输出 IR
```

Pass 可按 `ModuleOp`、`func::FuncOp` 等锚定不同层级。锚定类型决定 `getOperation()` 返回的对象和调度层级；Pass 可通过嵌套 pipeline 对子操作运行。

### 2. Pass 的职责与副作用

- Analysis Pass 读取 IR 并产生信息。
- Transform Pass 修改 IR。
- Verification/diagnostic 逻辑检查约束并提供错误信息。
- Pass 应遵循其作用范围、依赖 Dialect、失败传播和并行调度规则。
- 改 IR 时应使用 MLIR 支持的重写/修改机制；不能任意绕过通知机制，否则缓存分析可能失效。

### 3. 遍历和匹配

- `walk` 递归访问嵌套操作，适合简单查询和统计。
- typed walk 可只访问某个操作类型；通用 walk 可检查任意 Operation。
- 通过 operands 的定义者识别局部数据流，是基本 pattern 检查；它不自动处理复杂控制流、跨 Block、别名或副作用。
- 分析结果应明确边界：只统计 Operation 数量、检查局部生产者关系，还是进行全局数据流分析。

### 4. Pass 注册与插件

- Pass 需要注册才能按名称放入 pipeline。
- Pass 插件提供动态加载入口，适合把自定义 Pass 编译成共享库。
- Dialect 插件与 Pass 插件用途不同：一个主要注册 Dialect，一个注册 Pass；实际插件也可以组合注册行为，须看入口和 API。
- `getArgument()` 是 pipeline/命令行使用的 Pass 名称；Pass pipeline 语法还包含锚定操作层级。

### 5. Pipeline 与依赖

Pass pipeline 描述执行次序和嵌套层级。Pass 若需要特定 Dialect，应声明依赖或确保 Context/Registry 中已注册。前置 Pass 可能改变后续 Pass 的输入假设，因此顺序会影响合法性和结果。

### 6. 正式 Analysis Framework（本日建立概念）

简单 `walk` 计算不等于 MLIR 的可缓存 Analysis。正式 Analysis 通常由 `AnalysisManager` 管理，Pass 可请求依赖分析；IR 变化后，分析可能失效，也可以声明哪些分析仍有效（preserved）。缓存复用和失效规则是后续专题，本日只需知道它存在。

### 7. Pass 失败与诊断

变换无法满足要求时应报告诊断并让 Pass 失败，而不是静默留下不符合假设的 IR。只读 Pass 通常不修改 IR；发生失败与是否已改变 IR 的处理也应设计清楚。

## 本日应能回答

1. Pass 的锚点是什么？它如何决定作用层级？
2. pipeline 为什么有顺序和嵌套？
3. 统计 Operation 和正式缓存 Analysis 有什么区别？
4. 为什么直接改 IR 可能破坏分析缓存？
5. Pass 插件和 Dialect 插件分别解决什么问题？

## 练习建议

设计一个只读 Pass，统计每种 Dialect 的操作数；再做一个局部数据流检查，并列出它无法处理的情况（如 BlockArgument、多使用者、跨 Block 控制流）。
