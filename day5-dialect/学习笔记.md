# Day 5：Pattern Rewriting 与图变换

## 本日目标

掌握 MLIR 中声明式局部改写的基本模型，并理解从匹配一个 Operation 到识别一段 def-use 子图、再安全替换 IR 的过程。

## 知识点

### 1. Rewrite Pattern 的基本结构

Pattern 通常指定一个锚点操作，在 `matchAndRewrite` 中检查属性、类型、相邻 def-use 关系和语义条件。匹配失败返回 failure；成功时通过 Rewriter 修改 IR 并返回 success。

Pattern 不应依赖文本 SSA 名字，应使用 Value、Operation、类型、属性和接口进行判断。

### 2. PatternRewriter 与 IR 修改

- 创建新 Operation、替换结果、擦除旧 Operation、调整插入点等操作应通过 Rewriter API。
- `replaceOp` 会把旧结果的 uses 替换为新值并移除旧操作；替换结果数和类型必须匹配约束。
- `eraseOp` 要求操作没有仍被使用的结果；否则 IR 会变得无效。
- Rewriter 同时向重写驱动提供变更通知，支持 worklist、listener 和一致性维护。
- 匹配失败前不要留下部分修改；成功路径必须保证 IR 合法。

### 3. 子图匹配

子图通常通过 def-use 关系匹配，例如 `conv → add → relu`。匹配要检查：

- 中间值的使用次数和额外用户；
- 操作数位置与语义（残差分支是哪一个）；
- 类型、shape、layout、属性是否兼容；
- 区域/副作用语义是否允许融合；
- 替换后外部使用是否仍能得到等价结果。

“看起来相邻”不等于是可安全融合的子图；IR 中的拓扑由值的 uses/operands 决定，而不是文本行紧挨着。

### 4. Rewrite Driver 与不动点

Pattern 本身只描述一次改写。Greedy driver 管理待处理操作并重复应用 pattern，尝试达到不再变化的不动点。驱动器选项、区域边界、迭代上限和死代码处理行为要以当前 MLIR 版本/API 为准；不要假设所有驱动器都会自动执行任意 DCE。

### 5. Pattern 之外的变换方法

- 手工遍历和改写：适合简单、一次性变换，但需要自行管理顺序和合法性。
- Greedy pattern rewriting：适合局部规则集合反复收敛。
- Dialect Conversion：用于声明合法性目标并驱动跨方言 legalization，是后续 day7 内容。
- Canonicalization：遵循 MLIR 约定、由通用机制运行的规范化规则，后续专门学习。

### 6. 融合与语义保持

算子融合将多个计算替换为一个更粗粒度的操作，目标可用于后续优化或硬件映射。融合必须保持可观察语义，包括浮点细节、NaN/有符号零、广播、量化、内存副作用、shape 和用户关系。学习示例常简化这些约束，不能直接套用到生产级编译器。

### 7. Pattern 的可维护性

把匹配条件拆成清晰的小检查；为成功和失败路径准备 IR 测例；限制 pattern 的重写方向以避免循环；用 verifier 和 `FileCheck`/输出检查保证结果形状。Pattern 优先级/benefit 在竞争规则中可能影响选择。

## 练习建议

先写 `x + 0 → x` 的局部规则，再做一个两到三节点子图匹配。为每条成功规则准备至少一个负例：额外用户、类型不匹配或次序不符；运行后检查 verifier 和 IR 输出。
